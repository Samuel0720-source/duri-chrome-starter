# Architecture and decision log

## Code and data flow

| Request | Path | Why |
|---|---|---|
| See the anniversary from the Chrome toolbar (P1) | Local extension popup → date functions bundled at build time → extension-only storage, only if the user chooses to remember | The chosen date is still there when the popup reopens. Counting from the first day needs neither the web server nor room permissions. |
| Move to the small window or the full web app (P1) | Popup → `/compact` or `/` on the fixed web origin → the app validates only the first day and time zone in the URL fragment → the same CalendarPreview | No second calendar implementation or separate login token per screen. The fragment is never sent in the HTTP request. After sign-in (P2) the authenticated web app reads the real room from the server. |
| Open the website or installed app | Chrome → Next.js App Router on Vercel → the same start URL | One codebase serves a large tab, mobile and a small standalone window. The first PWA already computes real anniversaries. |
| Sign in and join a room (P2) | Supabase Auth → user session → database/RPC with the user's own rights → PostgreSQL | Room changes commit in a transaction. "Is this an authenticated user" and "which room do they belong to" are checked separately. |
| Shared activities (P2 onward) | Client command → server validation and DB commit → Supabase Realtime event on the room's private channel → re-read from the DB if needed | Realtime is the fast notification; the database is the confirmed state. After a short disconnect the screen recovers from the latest revision. |
| AI and places (P5) | Next server → membership, consent and budget reservation → external API → validated response → store and settle usage | Secret keys and spending limits stay on the server. The client only receives allowed data. |
| Mini golf (P6) | Shot id, angle, power, physics version → one short HTTP request → compute that shot's path and stop point → commit → both browsers replay the path | Both people can shoot at the same time without a 60 fps server loop. You can only hit your own ball once it has stopped. |

**Hosting.** Vercel announced general availability of WebSockets in Functions on 2026-10-20, but connections are still bound by a function's maximum run time. Duri uses Supabase Realtime so that auth, row-level security and realtime live in one place and operations stay simple. [Vercel announcement](https://vercel.com/changelog/websocket-support-is-now-generally-available) · [Limits of persistent connections](https://vercel.com/kb/guide/do-vercel-serverless-functions-support-websocket-connections)

**Boundary between Chrome and the web.** Web install metadata lives in `src/app/manifest.ts`; extension permissions and the popup live in `extension/manifest.json`. The popup opens a new tab or small window directly, and the installed PWA starts at the root URL. The extension's only API permission is `storage`, to remember the chosen date on this device. It does not touch auth cookies, room data or other sites the user is browsing. The extension source and the website share the same date functions, so the leap-day rule changes in exactly one place. For a public release the extension is rebuilt against the verified HTTPS address. [Chrome popup](https://developer.chrome.com/docs/extensions/develop/ui/add-popup) · [Tabs permission](https://developer.chrome.com/docs/extensions/reference/api/tabs) · [PWA manifest](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)

**Deployment address (P1).** Deployment Protection stays on. Preview URLs change with every deploy and may require a Vercel login, so the extension and phone checks use the fixed production address `https://duri-chrome-starter.vercel.app`, which opens without a Vercel login. The extension bakes that address into `origin.js` at build time; if the address changes, rebuild with `npm run extension:build -- <address>`.

**Shot contract.** The server fixes the course version, integer or fixed timestep, maximum steps and stop condition. It stores the raw input, start position, shot id, server start time, end position, elapsed time and stroke count. The unique shot id and the per-player version check are applied atomically. The client animates using the same physics module and the server path. Balls do not collide with each other. When both players finish a hole at the same moment, completion and records are committed exactly once in a per-hole transaction. One-hole and three-hole records are kept separately.

## Where code goes

The README lists where things live today. When a feature grows, group its UI and commands under `src/features/<feature>/`, keep domain rules in `src/core/`, and put adapters that use secret keys in `src/server/`. Keep external API handlers in `src/app/api/` thin. New tables and permission changes go into versioned migrations. Only create folders a phase actually needs.

### P2 · Accounts, rooms, invites, realtime (2026-11-11)

- **User problem:** Two people see the same room from their own devices and need to know right away when the other joins or leaves. Email links alone hit the default mail limit (a few per hour), which does not scale.
- **Data path:** Google → Supabase Auth (`/auth/v1/callback`) → app `/auth/callback` (code exchange, cookie) → the `/room` server component reads only its own seat through RLS → invite via `issue_couple_invite` (only a hash of the token is stored) → `accept_couple_invite` (locks the room row `for update`) → a `couple_members` trigger signals the private topic `room:<id>` with `realtime.send` → a `realtime.messages` policy lets only that room's members listen → the browser's `RoomLive` calls `router.refresh()`.
- **Approach and alternatives:** Broadcast instead of `postgres_changes`. On an RLS-enabled table, DELETE events can carry primary keys without filtering, which risked leaking user ids from other rooms. The signal only says `insert`/`delete`, and the screen re-reads from the server.
- **Tests that reproduce failures:** two people accepting the same invite at once (DB test, exactly one succeeds); a third party, a wrong topic, and a member who has left are all refused (DB); on the live site, A's screen updates without a reload (`FLOW_URL=... npm run test:flow`, passed in 18.9 s).
- **Limits:** Email sign-in has an hourly limit until custom SMTP is set up. Changes made while the realtime connection is down appear on the next refresh.
- **Interview answer draft (P2):** Both acceptance requests queue on the `couple_rooms ... for update` lock inside `accept_couple_invite`; the second one runs after the lock is released, sees the seats are full, and fails. The test checks with `pg_stat_activity` that the two requests really wait on that lock.

### P3 · Room home, chat, "guess your partner's pick" (2026-11-11)

- **User problem:** Two people keep plans, mood, chat and games going in one room, and the game is only fun if you cannot see your partner's answer early.
- **Data path:** Every write is a `security definer` RPC (checks membership and that the room is open) → a trigger sends a name-only signal (`room`/`plans`/`messages`/`guess`) to `room:<id>` with `realtime.send` → on a signal the browser re-reads from the server (`router.refresh()` for home, rows after the last id for chat, `guess_state()` for the game).
- **Approach and alternatives:** Instead of hiding answers in a public table with RLS, they live in a private schema and leave only through one read function. RLS is row-level, so hiding just the partner's answer column in the same row is awkward, and a path through the table API would remain. Chat uses a request id (`client_id`) so a resend does not duplicate a message.
- **Tests that reproduce failures:** when only A has answered, B's `guess_state` JSON has no A choice, direct reads of the private table are refused, and signals carry no answers (DB). Resending the same request id returns the same message id; 10 messages per 10 seconds limit (DB). On the live site two browsers see plans, mood, chat and the game update instantly (flow test).
- **Limits:** The 30-day cleanup of shared data in closed rooms does not exist yet. Chat loads only the last 50 messages at first.
- **Interview answer draft (P3):** Before both answers are in, the partner's browser receives only `partnerAnswered: true` and `partner: null` for that round. The real choice exists only in the private schema, and `guess_state()` returns it only for rounds both people have answered.

### P4-1 · 100-second drawing quiz (2026-11-12)

- **User problem:** At the same moment one person draws and the other guesses. If the word leaks the game is ruined, and if the clock can be cheated the records mean nothing.
- **Data path:** The drawer moves the pen → every 150 ms the browser sends stroke pieces to the `add_draw_stroke` RPC (each piece has a uuid, so resends are ignored) → the DB checks it is the drawer, before the deadline, and within coordinate bounds, then stores it in `draw_strokes` → a trigger publishes an empty `draw` signal on `room:<id>` → the guesser's browser re-reads the strokes in 120 ms batches and redraws the canvas. Guesses go through `guess_draw`, which normalizes and compares in the DB.
- **Approach and alternatives:** (1) Putting stroke coordinates straight into Realtime messages is faster, but nothing survives a reload and it is hard to control what remains in a closed room, so it was dropped. Storing strokes and sending only a signal restores the same drawing after a reload or on another device (cost: drawing appears in 150 ms steps). (2) A word list in `src/core` would ship every possible answer in the browser bundle, so the words live in a private table. (3) A browser timer can be cheated, so the DB sets the deadline with `clock_timestamp()` and the screen corrects for the offset from DB time.
- **Tests that reproduce failures:** the word appears nowhere in the guesser's state JSON, rows or signals; resending a stroke piece stores one row; two identical correct guesses at once yield one `correct` and one `closed` (one result); a guess after moving the deadline into the past gets `closed`; reading the state alone closes an expired round exactly once; every call from a third party is refused (DB). On the live site, no server response to B contains the word (flow test).
- **Limits:** Drawing feel on touch devices and stroke latency across distant networks are unmeasured. An expired round closes when someone next reads the state or guesses (no background job).
- **Interview answer draft (P4-1):** When a correct guess and the timeout arrive at the same instant, both try to lock the `draw_games` row `for update`, so one waits. The first writes the result under `where result is null`; the second then sees a result already present and gets `closed`, so the result is stored exactly once.

### P4-2 · YouTube watch together (2026-11-12), end of P4

- **User problem:** Two people in different places watch the same scene of the same video at the same moment. When one pauses or skips, the other follows. Leaving and coming back resumes where they were.
- **Data path:** One person pastes a link → the browser checks the format first → `watch_set_video` re-parses it in the DB and stores the video id (+revision) → both call `watch_ready` → on the second ready the DB sets `playing = true` with the reference time taken from the DB clock (+revision) → a trigger sends an empty `watch` signal to `room:<id>` → each browser re-reads `watch_state()` and classifies the revision (stale / own / apply) → only `apply` moves, plays or pauses the official YouTube IFrame player. A human action goes out as `watch_command` (request id, position) and bumps the revision. Every 20 s there is a `watch_ping` (presence) and a re-read. When the last person leaves, or after 45 s without a ping, `settle_watch` saves a paused state at the last watched position.
- **Approach and alternatives:** (1) Constantly broadcasting the position accumulates delay and reordering and cannot restore after a reconnect, so only "reference position + reference time + playing" is stored and the current position is computed (nobody streams positions during playback). (2) Browser clocks can be wrong, so the DB sets the reference time and the screen corrects for its offset. (3) Detecting play/pause only from player events mistakes our own moves for human actions and the screens echo each other forever. So for 1.2 s after we move the player its events are ignored, no command is sent if the state already matches, and the server revision filters out what was already applied or sent by me.
- **Tests that reproduce failures:** resending the same request id bumps the revision once; taps within 150 ms are refused; when both leave the position is saved, and 45 s of silence pauses (DB). Local revision classification, the 1.0 s rule (exactly 1.0 is kept) and the 3 s rule (unit). Ready → play → pause → seek → reload and rejoin → recovery from an embed-blocked video in two browsers (live site, fake player).
- **Limits:** Ad and buffering signals are incomplete, and the real YouTube player's event order needs a human check. If a tab closes suddenly the "leave" request may be cancelled, so the 45 s timeout pauses instead.
- **Interview answer draft (P4):** When I receive my partner's seek and move my player, the player fires its own event; treating that as my action and sending it back makes the two screens keep undoing each other. So (a) anything at or below a server revision already handled, or a command I sent, is ignored; (b) for 1.2 s after I move the player its events are not treated as human input; and (c) the periodic check only corrects when the gap exceeds 1.0 s and 3 s have passed since the last automatic correction. Human play, pause, seek and reconnects apply immediately with no cooldown.

### P5-1 · Spending-limit ledger (2026-11-13)

- **User problem:** AI and place searches cost money per call. A leaked key, a bug or concurrent requests must never be billed beyond the budget.
- **Data path:** Right before a paid call the Next server calls `reserve_api_call(room, kind, request key, worst-case cost)` (service_role) → the DB locks the settings row, checks billing is on, prices, per-room/day counts and the project/month total, and records a reservation in `api_ledger` → only then does the external API get called → afterwards `settle_api_call` (actual cost), or `release_api_call` only if the provider was never reached. The screen sees only counts and percentages through `api_usage`.
- **Approach and alternatives:** (1) In-memory or Redis counters cannot see each other across servers and vanish on restart; every server uses the same PostgreSQL ledger, serialized by a single row lock. (2) Counting after the call is too late; the worst-case cost is reserved first and settled later. (3) Cloud billing alerts notify but do not block, so the app-level ledger is the main guard and alerts and provider quotas are backups. (4) Releasing a call whose response never arrived leaks budget if it was in fact billed, so a release happens only when the provider was certainly not reached; otherwise the worst case stays reserved.
- **Tests that reproduce failures:** with 4 cents left in the monthly budget, three 4-cent requests at once let exactly one through and the total never exceeds the budget; resending the same key counts once; settling twice is impossible; members, anon and third parties cannot call the functions or read the tables directly (DB). On the live site the helper tab shows the AI-off state (flow).
- **Limits:** Real AI and place calls are not connected yet (prices and budget undecided). The 80% alert and provider-side quotas are not configured. Prices are integer cents, so very cheap calls are rounded up to stay conservative.
- **Interview answer draft (P5):** Two requests racing for the last share of the budget both try to lock the same settings row `for update` inside `reserve_api_call`. One checks the total, records its reservation and commits; the waiting one recomputes with that reservation included and is rejected as over the limit. The external call only happens after a reservation passes. The test fires three at once and confirms exactly one gets through.

### P6-1 · Gomoku (2026-11-13)

- **User problem:** In a turn-based game, simultaneous taps or a network resend of the same tap must never break the board.
- **Data path:** Pick a cell (preview) → "Place here" → `play_gomoku(game, x, y, request id)` → the DB locks the game row `for update` and checks (1) the same request id means `duplicate`, (2) it is my turn, (3) the cell is empty → records the stone → counts same-colour stones in four directions; 5 or more is `won` (winning line stored, record +1), 225 moves is `draw` → a trigger sends a `gomoku` signal (no coordinates) → the partner's browser re-reads `gomoku_state()`.
- **Approach and alternatives:** Deciding the winner in the browser allows tampering and lets the two screens disagree, so it lives in a DB function. Re-reading state instead of sending stone positions in the signal is the same path used for reloads and other devices. On mobile, one tap previews and a confirm button places, preventing mis-taps.
- **Tests that reproduce failures:** the same player tapping two cells at once places one stone (lock); resending a request id leaves one stone; moves on a finished game are refused; the win record increases once.
- **Limits:** The slowest part is re-reading the full state (stone list) every move, at most 225 stones. No undo, time limit or forbidden-move rules.
- **Interview answer draft (P6-1):** If both players try to place a stone at the same moment, both try to lock the same game row `for update`, so one goes first. The other, once the lock is released, sees the turn has changed and gets "Not your turn". A resent tap carries an existing request id and returns `duplicate`, so only one stone remains.

### P6-2 · Simultaneous mini golf (2026-11-13)

- **User problem:** Even when both people hit at the same moment, each screen must show the same ball movement, and ball positions must survive a reload or reconnect.
- **Data path:** Drag (angle, power) → `golf_shot(game, shot id, angle, power)` → the DB locks my ball row `for update` and checks it is not already holed or still rolling → computes the full path **once** with fixed physics (1/60 s steps, 3 substeps, friction 0.985, 75% bounce) → stores the path and the DB time it ends → a trigger sends a `golf` signal (no coordinates) → both browsers read the path via `golf_state()` and replay it **on the DB clock**.
- **Approach and alternatives:** (1) If each browser runs physics, results differ per device (floating point, frame timing). (2) A server streaming at 60 fps is costly and laggy. So: compute once, store the path, everyone replays. The computation lives in a DB function rather than the Next server because it needs no secrets, shares a transaction with the write, and can be tested against an embedded PostgreSQL. Balls pass through each other so two people's shots never change each other's outcome, which removes ordering problems with simultaneous input.
- **Tests that reproduce failures:** two simultaneous shots produce the same paths as each one simulated alone; a resent shot id counts one stroke; hitting while rolling is refused; the next hole does not start before the replay ends; the best score updates only when it improves.
- **Limits:** The path is sampled every 50 ms and linearly interpolated (small curvature error); 3 fixed courses; shots are computed in PL/pgSQL with a 500-tick cap (about 8 s); the physics version is stored as `physics=1` so it can change later.
- **Interview answer draft (P6-2):** "How did you guarantee the same picture when physics differs per browser?" The browsers do not run the physics. The DB runs a deterministic simulation once per shot and stores the path; both browsers only replay it against the DB clock. The same input gives the same path (tested), and a resent shot id returns the stored path.

### P6-3 · Feedback round (2026-11-13)

- **Removing stutter:** The screen computes the ball position from "DB clock = my clock + offset". Re-estimating the offset on every response made the ball jump whenever a response was slow. Like NTP, only the measurement with the shortest round trip (smallest error) is trusted, and a shot learned about late replays from the start instead of skipping. The DB decides the final position, so both screens end the same.
- **"A different question or word every time":** Pure randomness repeats quickly (the birthday problem). Each room picks the item whose "last seen" time is oldest (LRU), so nothing repeats until the whole bank has been used.
- **Keeping the drawing quiz secret:** With several words per round, the current word goes only to the drawer and past words go to both. Strokes and guesses carry the word number, so the next word starts on a blank board.
- **Interview answer draft (P6-3):** "How did you find and fix stutter in a realtime screen?" I split the cause into four: clock-offset jitter, an extra round trip for the shooter, skips caused by late signals, and coarse path samples. I fixed them with minimum-round-trip measurement, including the replay time in the response, delaying late replays, and storing the path every tick, and pinned the clock rules with unit tests.

### P7 · Language, nicknames, read receipts, video sources, instant prediction (2026-11-13)

- **Language:** No library; `src/i18n/`. The server picks ko or en from the `duri_lang` cookie, falling back to `Accept-Language` (`pickLocale`), and hands the same dictionary to the client. The English dictionary is typed `Record<keyof typeof ko, string>`, so a single missing key fails the type check. Korean particles (`{이/가}` and so on) are chosen from the final consonant of the nickname. The extension popup cannot read web cookies, so it follows Chrome's language.
- **Nicknames and read receipts:** One `member_prefs(room, user)` row holds "the nickname I use for my partner" and "the last message id I have read". Direct writes are blocked; only RPCs (length and control-character checks; the read position only moves forward and never past the newest message). Changes send a `prefs` signal and the partner re-reads. Messages are marked read only while the screen is visible and focused, so a background tab never claims "read".
- **Video sources:** The DB parses a link into `(source, ref)` (`parse_video`), and the screen drives YouTube, Vimeo and `<video>` through one adapter with the same state number. The sync rules (position + elapsed time, correct only gaps over 1 s) stay unchanged. Files must be https with a video extension.
- **Instant golf prediction:** Copying physics to the client risked per-device differences, so the order of operations and constants were ported exactly from the DB and 270 shots are tested to match. The DB path is still the truth; prediction only hides the wait.
- **Interview answer draft (P7):** "How did you remove input lag in a server-authoritative game?" Client-side prediction: the same deterministic physics runs in the browser first and is shown immediately, and a test (270/270) guarantees it matches the server. If the server rejects a shot, the prediction is dropped and the screen returns to the server state.

### P8 · Album, room background, passwords, Netflix (2026-11-14)

- **Album data flow:** Pick photos → the browser redraws them as 1600 px and 480 px JPEGs (dropping GPS and other camera data) → uploads directly to Storage `room-photos/<room>/<photo>.jpg` (policy: members of that room only) → `add_room_photo` checks the file really exists and adds it to the list (200-photo limit) → `photos` signal → the partner's screen refreshes. For display, `/api/photo/<id>` fetches with the signed-in user's rights and serves a stable URL. Signed URLs change every time, which would re-download the background on every page; the stable URL is cached by the browser (`private`).
- **Background:** One `couple_rooms.wallpaper` column (same `room` signal as the theme). Deleting the photo clears the background automatically through the foreign key's `on delete set null`, so a deleted photo can never remain as the background.
- **Closing a room:** A DB function cannot really delete Storage files (only metadata), so a server action empties the folder with the member's rights *before* the room closes, and the room does not close if that fails.
- **Passwords:** At least 8 characters (app and Supabase), and anything over 72 bytes is rejected (bcrypt only reads 72 bytes and silently drops the rest). Errors appear in the URL only as short codes (`?error=wrong`), never raw messages. Sign-up and reset responses look the same whether or not the email exists, so membership cannot be probed.
- **Netflix:** Netflix cannot be embedded in another site (DRM), and sharing an account breaks its terms. So, like Teleparty, each person plays in their own tab and the extension relays. Netflix tab (a MAIN-world script seeks with Netflix's own player; setting `<video>.currentTime` makes Netflix stop with an error) ↔ bridge script ↔ background switchboard ↔ bridge on the Watch together page ↔ the page's `netflix` adapter. The adapter has the same shape as the other players, so the sync rules (revision, 1 s correction) are unchanged. The extension permission is still just `storage`; the scripts run only on `netflix.com/watch/*` and this site's `/room/watch*`, and the release checker blocks any other page.
- **Interview answer draft (P8):** "How did you sync a third-party player you cannot control (Netflix)?" I left the sync logic alone and abstracted "the player" behind an adapter. The Netflix adapter sends commands and receives state through extension messages instead of a real video element. Each boundary (page ↔ extension, extension ↔ Netflix) re-checks the command type and number ranges, and a fake Netflix page lets the browser tests run in CI without an account.

### Daily postcard and one-to-one calls

Both people get the same question based on the room's local date. Question answers and game scores are saved through the existing chat write path when the user chooses to send them.

Call events were added to the chat screen's existing private subscription. `signal_room_call` checks the two seats and the caller's eligibility, then publishes a signal whose kind and size are limited. After accepting, both browsers ask for the microphone, and for the camera only in video mode. WebRTC's encrypted media goes device to device; there is no media server or recording storage. (A TURN relay was added later; see below.) If a direct connection is blocked, a timeout notice appears. Likely question: when both devices call at the same moment, how is a single invitation chosen?

### Mail-bird garden and the postcard match

Seven postcard pairs are shuffled by the server every game. The browser receives only face-up cards, both scores and whose turn is next. The turn passes after every two flipped cards, and a mismatched pair turns back over after 1.5 s. Each input sends the last revision it saw and is processed after locking the room row. Receiving a private broadcast or reconnecting reads the same state. Interview question: why does a rematch pressed on both devices at once create only one game?

Each received audio track is attached to its own audio element. The video preview is muted and the partner's voice plays in exactly one place. If autoplay is blocked, a button appears to play the partner's audio directly.

### Call relay (TURN) · 2026-11-14

- **Problem:** Calls used only STUN, so if either side was on a strict network (mobile data, school Wi-Fi, symmetric NAT), the two devices could not find each other and the call hung at "connecting" or had no sound. Tests on one computer or one Wi-Fi always passed, so it stayed hidden.
- **Fix:** For each call, `/api/call/ice` fetches one-hour relay credentials from Cloudflare TURN (keys only in server environment variables: `CLOUDFLARE_TURN_KEY_ID`, `CLOUDFLARE_TURN_API_TOKEN`). When a direct path works the browser uses it on its own; the relay is used only when it does not. If the keys are missing or Cloudflare fails, it falls back to STUN only.
- **External paid call record (every paid external call is recorded here):** Reason: connecting calls across different networks. Scope: only signed-in people in a two-person room, one request per call, credentials valid one hour. Cost: Cloudflare TURN is free up to 1,000 GB a month, then USD 0.05 per GB (an hour of voice ≈ 0.03 GB, video ≈ 0.5 to 1 GB). Checks: `tests/unit/ice.test.mjs` (port 53 removed, credentials required) and a real voice call in the live flow (audio playback confirmed, connection path shown).
- **Interview answer draft:** "Tests passed, so why did real users' calls fail?" The two test browsers were on the same machine, so address exchange (STUN) was enough. Two real people can sit behind different NATs with no direct path, and then a TURN server must relay the media. The screen now shows the type of the connected candidate pair (host/srflx vs relay) so the next failure is easy to tell apart.

## P9 · Number baseball

- **Data flow:** Screen → `baseball_action(room, revision seen, 'secret' | 'guess', digits)` → the server scores against the secret number and bumps the revision → a trigger sends an empty `baseball` notice on the room channel → both screens re-read `baseball_state`. The state is built per person: you get only your own secret, and the partner's arrives only after the game ends.
- **Design reasons:** Scoring in the browser would require sending the partner's secret to the browser, where developer tools could read it. So the server judges, and the screen shows the guess immediately (optimistic display) and waits only for the result. A guess with a stale revision changes nothing, so double taps are safe. A secret belongs to one seat, so it is accepted whenever that seat is still empty, even if the partner's secret landed first (fixed 2026-11-24).
- **Interview question:** "In a real-time two-player game with information hidden from the opponent, how would you split the work so you never trust the client but the screen still reacts instantly?"

### Popup chat sizing and startup · 2026-11-23

At widths up to 560px, Chat uses the available viewport minus the measured persistent call dock. The room shell and history can shrink; the composer, question draft and error stay outside the history scroller. History scrolling never scrolls the surrounding document. Incoming messages follow the bottom only when the reader was already near it. Idle toolbar calls use one handoff button; calls still live in the persistent room layout in the separate small window.

The toolbar caches only sanitized route, language and theme in extension-local localStorage, with chrome.storage.local retained for migration. A missing cache gives storage at most 100ms before starting the iframe. Late preferences cannot reload a screen the user is interacting with. Surface messages are deduplicated, avoiding writes on each chat/render mutation. No permissions or credential storage were added. This removes a local startup dependency, not server/network cold-start time.

Review question: why must message scrolling and call-dock resizing never move the composer underneath the dock?

### Compact call launcher (0.5.4)

Both toolbar detach and the embedded call button send the existing open-small message to the packaged worker. The worker owns one popup ID in session storage, explicitly requests normal state and 440×600 outer bounds, then normalizes and reapplies those bounds after creation. Reusing the popup never navigates it, so its media stream survives. A resize failure must not create a second call owner. Native tests assert Chrome window bounds, not an emulated Playwright viewport. No new permissions or stored credentials. Interview question: why must normalizing a fullscreen window happen before applying dimensions, and why must reopening avoid page navigation?
