# Claude Code 세션과 인계 템플릿

`CLAUDE.md`는 매번 필요한 지침, `STATUS.md`는 실제 진도, `ARCHITECTURE.md`는 결정을 내린 이유다. 대화가 새로 시작되거나 다른 에이전트가 맡아도 이 파일들을 보면 같은 지점에서 이어갈 수 있다.

## 그대로 복사할 메시지

**첫 세션 · 읽기와 범위 정하기**
> phase-planner 에이전트를 사용해. CLAUDE.md와 docs/STATUS.md를 읽고 Chrome 도구 모음 → 작은 창 → 전체 웹앱 경로에서 현재 구현한 파일, 아직 확인해야 할 행동, 검증 명령을 알려줘. 오늘 내가 할 일 한 개로 끝내 줘.

**선택한 작업 구현 · 메인 Claude Code**
> 이번 작업은 [한 사람이 할 행동]이야. 성공은 [눈으로 확인할 결과], 실패 사례는 [재현 조건]이야. 관련 파일과 기존 테스트부터 읽고, 이 범위만 구현해. qa-runner로 검사하고 docs/STATUS.md에 실제 결과를 남겨 줘.

**DB 변경 검토**
> data-reviewer 에이전트로 남은 초대 한 자리에 B와 C가 동시에 들어가는 경로를 검토해. DB 트랜잭션, 다시 보낸 같은 요청, 제3자의 직접 읽기를 각각 어떤 테스트가 확인하는지 알려줘. 이미 열린 채널에서 방을 나간 뒤 접근할 수 있는지도 살펴봐.

**다음 날 이어하기**
> docs/STATUS.md의 ‘다음 작업 하나’를 읽고 해당 경로가 현재도 존재하는지 확인해. 마지막 검사 결과와 오늘의 통과 기준을 확인한 뒤 진행해. 코드가 상태 문서와 다르면 실제 파일을 기준으로 문서를 고쳐 줘.

## 한 작업용 빈 카드

```text
현재 단계와 목표:
누가 어디서 무엇을 하는가:
읽을 파일(2~5개):
바꿀 범위:
성공 시 화면 또는 데이터:
실패·재시도·상대 사용자에게 보일 것:
실행할 명령:
직접 확인해야 하는 기기/브라우저:
인계할 경로, 결정 이유, 다음 한 가지:
```

예를 들어 ‘미니 창 날짜 변경’의 성공 기준은 **서울 시간대로 2024-02-29를 고른 후 전체 웹앱을 열어도 날짜와 시간대가 그대로 보이는 것**이다. 관련 경로는 `src/app/preview.tsx`, `src/core/preview.ts`, `tests/browser/extension.spec.ts`다. 브라우저에서 확인할 동작을 먼저 적으면 에이전트가 어느 파일을 왜 읽어야 하는지 좁혀진다.

## 역할을 하나 더 만들 때 쓰는 형식

기본 세 역할은 이미 `.claude/agents/`에 들어 있다. 같은 검토를 반복하게 될 때 다음 예처럼 `.claude/agents/surface-reviewer.md` 하나를 만들어 확장할 수 있다. 이름, 위임 조건, 읽을 경로, 결과 형식, 도구 범위를 분명하게 적는다. [Anthropic 에이전트 파일 형식](https://code.claude.com/docs/en/sub-agents)

```markdown
---
name: surface-reviewer
description: Review changes that move a user from the Chrome popup to the mini window or full web app.
tools: Read, Glob, Grep
---
본인 역할은 화면 사이 이동 경로의 읽기 전용 검토다.
CLAUDE.md와 docs/STATUS.md를 읽고 extension/, src/core/preview.ts,
src/app/compact/, tests/browser/extension.spec.ts에서 관련 파일을 고른다.
선택한 날짜가 언제 어디로 넘어가는지 확인한다. 발견마다 재현 순서,
관련 파일, 사용자가 보게 될 증상, 확인할 테스트를 메인 세션에 반환한다.
```

## 설계 기록 빈칸

**사용자 문제 → 실제 데이터 흐름 → 선택한 방법과 이유 → 검토한 대안의 비용 → 실패를 재현한 검사 → 내 말로 설명할 질문 하나.** 실측한 항목은 명령·환경과 함께 남긴다. 키, 초대 토큰, 정확한 위치, 커플의 대화 내용은 예제로 기록하지 않는다.

## 다른 프로젝트용 CLAUDE.md 뼈대

아래 내용을 그 프로젝트의 루트 `CLAUDE.md`에 옮겨 실제 파일명과 명령으로 채운다. 이미 있는 지침이 있으면 같은 항목에 내용을 합친다.

```markdown
# [프로젝트 이름]
사용자가 [무엇]을 할 수 있도록 [제품]을 만든다.

## 먼저 읽을 것
1. [현재 상태 파일]에서 다음 작업 하나와 마지막 검사 결과를 읽는다.
2. 해당 단계의 [완료 기준 파일]에서 이 기능에 필요한 부분만 확인한다.

## 코드 지도
| 사용자 행동 | 진입 파일 | 상태를 결정하는 파일 | 가장 가까운 테스트 |
|---|---|---|---|
| [행동] | [화면/명령] | [도메인 규칙/DB] | [테스트 파일] |

## 실행과 검증
개발 실행 [명령]. 빠른 검사 [명령]. 전체 검증 [명령].
사용자가 직접 확인할 경로 [기기와 조작 순서].

## 설계 이유와 인계
유지할 결정 [원칙과 이유]. 메인 세션은 변경을 통합한다.
인계에는 실제 바뀐 파일, 실행 결과, 다음 작업 하나를 남긴다.
```
